# 04 — Engineering Practices

These practices apply to every ticket, whether a human or an agent writes the code. Agents build and merge
tickets without a human check ([ADR-0014](./adr/0014-autonomous-agent-workflow.md)), so these rules are
enforced by tooling (CI, branch protection, fitness tests) and by independent review, never by anyone's memory.

## 1. Git workflow: trunk-based

- `main` is always releasable. CI builds and smoke-tests the production image on every PR and merge (P1-08).
  From milestone D, a merge to `main` also deploys to staging.
- **Short-lived branches** last at most 2–3 days. Branch from `main` and **rebase onto the latest `main`
  before merging**. This is required, not just tidy: CI and the review then ran against the code that
  merges. The explanation describes the PR at its recorded source revision, not the merged tree.
- **Delete the long-lived `develop` and `staging` branches** (P0-04). Environments are deployments, not branches.
- **Branch name:** the ticket ID in lowercase plus a short slug, for example `p2-03-tenant-context` or
  `p5-02a-package-create`. Ticket IDs stay uppercase everywhere else (`P2-03`, file names, commit tags). Put
  the owner in the PR assignee field, not in the branch name.
- **Squash merge only.** The squashed commit message is the PR title. The agent merges once the
  [merge gate](./AI_AGENT_PLAYBOOK.md#step-7--merge-gate-agent-merges) passes.
- **Parallel agents:** use one `git worktree` per agent session
  (`git worktree add ../bw-p3-02 -b p3-02-email`), so agents never share a working directory.

### Commit and PR titles: Conventional Commits

```text
feat(packages): add atomic pickup endpoint [P5-02b]
fix(auth): revoke all sessions on password reset [P4-04]
test(tenancy): add cross-building fitness test [P2-03]
chore(ci): run alembic check [P0-05]
docs(adr): record session-cookie decision [P0-01]
```

Types: `feat`, `fix`, `test`, `refactor`, `chore`, `docs`, `perf`, `build`, `ci`. Inside a branch, agents may
make small WIP commits; the squash cleans them up.

## 2. Pull requests

| Rule | Why |
|---|---|
| One ticket per PR. ≤ ~400 changed **non-test** lines, excluding generated files and lockfiles. Tests don't count. | A reviewer (human or AI) catches more in a small diff, and a bad merge is cheaper to revert. Counting tests would push agents to cut them, the exact wrong incentive. Over the limit → split the ticket |
| PR template completed ([.github/pull_request_template.md](../.github/pull_request_template.md)), including the plan and "Decisions and alternatives" | The reviewer and the explainer get context, evidence and risks up front |
| CI green before the independent review | Reviewers don't spend rounds on what machines catch |
| Independent review by a fresh session returns `MERGE`; Tier 1 also needs Codex or a second reviewer ([05 §Step 5](./AI_AGENT_PLAYBOOK.md#step-5--independent-review-fresh-session-the-merge-paths-only-judge)) | No human reviews after it, so the reviewer must not share the author's context |
| Tier 1–2 user-reachable behaviour: the journey is run on the stack and the transcript is in the PR | Auth and tenancy bugs hide in paths tests don't cover |
| No protected gate loosened ([05](./AI_AGENT_PLAYBOOK.md#protected-gates)) | The agent merges its own work, so it must not edit the checks that judge it |
| Branch rebased onto the latest `main` before merge | CI and the review ran on what merges; the merge gate checks that nothing after the explanation changed what it describes |

**Branch protection on `main`:**
- PR required, with **no required approval** (the agent merges its own PRs once the merge gate passes;
  GitHub doesn't let an author approve their own PR anyway).
- Required status checks: `backend`, `frontend`, `docs`, `prodlike` (from P1-08), `e2e` (from P4-09).
- Branches must be up to date before merging.
- Linear history.
- No force push.

## 3. Definition of Ready (before an agent starts)

- The ticket has a goal, scope and out-of-scope, interfaces, Given/When/Then acceptance criteria and a test plan.
- Dependencies are merged, or their interface contract is merged.
- **Frame step done.** The agent has sharpened the acceptance criteria and recorded its Frame notes as the
  branch's first commit ([05 §Step 1](./AI_AGENT_PLAYBOOK.md#step-1--frame-implementer-no-code-yet)).
- Any product or tech decision the ticket needs exists as an ADR or a scope-doc entry, or is resolved by the
  [decision rules](./AI_AGENT_PLAYBOOK.md#decision-rules) without hitting a stop rule.

## 4. Definition of Done (every ticket)

- [ ] Acceptance criteria demonstrably met. The PR shows command output or screenshots.
- [ ] Tests are added and pass locally and in CI. For tenant data: the same-building and cross-building cases
      from the checklist below.
- [ ] Migrations are included, read and edited by the implementer (not just autogenerated), checked by the
      reviewer against the models, and reversible where practical. `alembic check` is clean.
- [ ] New settings are in `.env.example`, with secrets marked as secrets (they become SSM parameters in
      milestone D).
- [ ] OpenAPI is regenerated and the frontend types are committed if the API changed.
- [ ] The UI handles loading, empty, error (problem+json `detail`), 403 and 404 states, and works at mobile
      width.
- [ ] Logs carry no secrets or personal data beyond IDs.
- [ ] The independent review's final round is `MERGE`, with no open Critical or High finding.
- [ ] The explanation is written by a fresh session (full form for Tier 1–2, short form by default for
      Tier 3): the decisions with their recorded rationale, how it is implemented, the code, the review log
      and what was not verified. It names the PR and the source revision it describes.
      `scripts/check-explanation-refs.py` passes for it.
- [ ] The ticket index status is `done`, and autonomous decisions are listed in
      [HUMAN_INBOX.md](./HUMAN_INBOX.md).

**Learning is separate from Done.** James reads explanations, takes `/quiz-me` and marks "Learned" in the
index at their own pace; nothing waits on it.

## 5. Backend standards

- **Python:**
  - 3.14
  - type hints everywhere
  - `mypy --strict` on new modules; legacy files may be excluded at first
  - `ruff check` with rule sets `E, F, I, B, UP, S, ASYNC, SIM, RUF`
  - `ruff format`
- **Async:** use only async drivers in request paths (asyncpg, aiosmtplib, aioboto3 or boto3 in a thread).
  Never call blocking I/O in `async def`. Ruff's `ASYNC` rules flag common cases.
- **Pydantic:**
  - Separate `XCreate`, `XUpdate` and `XOut` schemas.
  - `model_config = ConfigDict(from_attributes=True)` on outputs.
  - Use `Field(max_length=…)` on every string input.
  - Never expose ORM objects or internal columns such as `password_hash`, `token_hash` or `s3_key`.
- **Errors:** raise domain errors from services (`NotFound`, `Conflict(code=...)`, `Forbidden(code=...)`).
  Only `core/errors.py` knows HTTP.
- **Transactions:** one `commit()` per write use-case, in the service. Helpers never commit.
- **Queries:**
  - Always filter by `building_id` from `TenantContext`.
  - Prefer `select()` 2.0 style.
  - Avoid N+1 with `selectinload` / joins.
  - Every list endpoint is paginated.
- **Naming:** tables are plural snake_case; enum values are lowercase snake_case; audit actions are
  `<domain>.<past_verb>`; job kinds are `<domain>.<verb>`.
- **Comments:** explain *why*, not *what*. Delete commented-out code, because git remembers it.

### Migrations (Alembic)

1. Change the models, then run `alembic revision --autogenerate -m "<imperative summary>"`. **Read and edit**
   the generated file. Autogenerate misses or garbles:
   - server defaults
   - partial indexes
   - `NULLS NOT DISTINCT`
   - check constraints
   - enum changes
   - data migrations
2. **Expand/contract for anything that could break the previous release.**
   - Expand: add a nullable column → backfill → set NOT NULL in a *later* release.
   - Contract: never drop or rename a column in the same release that stops using it.
3. Never edit a migration that has been merged to `main`: other worktrees and agents have already applied it
   locally, and from milestone D staging has run it. Write a new one instead.
4. If two branches both add a migration, the second to merge rebases and re-points `down_revision`, so there
   is one head. CI fails on multiple heads.
5. `downgrade()` is implemented for schema changes. It is for local development only, never run
   automatically in deployment.

## 6. Frontend standards

- **TypeScript** for every new or migrated file (`.ts/.tsx`). Legacy `.jsx` is allowed until its page migrates.
- **Data:**
  - Only through `src/api/client.ts` and React Query hooks in `features/<domain>/api.ts`.
  - No `fetch` in components.
  - No Base44 imports under `features/` (an ESLint rule enforces this).
- **Query keys** use building-scoped arrays (`['b', buildingId, 'packages', params]`). Mutations invalidate
  the exact keys they affect.
- **Forms:** `react-hook-form` + `zod` (already dependencies). Show the server's `detail`/`errors` next to
  the fields.
- **Accessibility:**
  - every input has a label
  - buttons are `<button>`
  - focus moves to dialogs and returns afterwards
  - status changes are announced (`aria-live`)
  - contrast passes
  - checked with the axe browser extension on each migrated page
- **Dependencies:** remove a Base44-era dependency once nothing imports it (stripe, three, leaflet, jspdf,
  html2canvas, moment, …). A smaller bundle loads faster.

## 7. Testing standards

**Every endpoint touching tenant data must have these tests** (helpers from P1-05 make each one a line or two):

| # | Case | Expected |
|---|---|---|
| 1 | Happy path for each allowed role | 2xx, correct body |
| 2 | Unauthenticated | 401 |
| 3 | Authenticated, member of **another building** | 404 |
| 4 | Same building, **wrong role** | 403 |
| 5 | Same building, **another resident's** record | 404 |
| 6 | Pending / suspended membership | 404 (operational routes) |
| 7 | Related ID from another building in the body (unit_id, file_id) | 404 or 422, and no row written |
| 8 | Invalid state transition | 409 `invalid_transition` |
| 9 | Duplicate / retry (where idempotency applies) | Original result, no duplicate row |
| 10 | Concurrency (where invariants apply) | Exactly one winner; the loser gets 409 |

**Other rules:**
- Test names describe behaviour: `test_resident_cannot_see_other_residents_package`.
- Use real Postgres, and do not mock the database. Mock only external providers (SMTP, S3 in unit tests).
- Every bug fix starts with a failing test that reproduces it.
- There is no coverage-percentage target. Use the table above and review instead.

## 8. CI pipeline (GitHub Actions)

| Job | Steps | Blocks merge |
|---|---|---|
| `backend` | `uv sync --locked` → `ruff check` → `ruff format --check` → `mypy` → `alembic upgrade head` + `alembic check` (single head) → `pytest` (Postgres service) → `pip-audit` | yes |
| `frontend` | `npm ci` → `eslint` → `tsc --noEmit` → `npm run gen:api` and `git diff --exit-code` → Base44 ratchet → `vite build` → `vitest` → `npm audit --omit=dev --audit-level=high` | yes |
| `prodlike` (from P1-08) | build the image (tag = SHA) and the SPA → `compose.prodlike.yml` up → `alembic upgrade head` from the image → `scripts/smoke.sh` (version = SHA, SPA fallback, cache and security headers) | yes |
| `e2e` (from P4-09) | prod-like stack up → seed → Playwright → upload traces on failure | yes |
| `restore-test` (from P7-01, weekly + manual) | seeded stack → `scripts/backup.sh` → `scripts/restore-test.sh` | no (scheduled) |
| `docs` (from P0-01) | `scripts/check-links.py` (relative markdown links) → `scripts/check-explanation-refs.py` on explanation files changed in the PR only | yes |
| `security` | gitleaks (secrets), Trivy (image, on main) | yes / advisory |
| `deploy` (main only, from milestone D) | build + push image (SHA) → frontend artifact → SSM deploy → `scripts/smoke.sh` | n/a |

Dependabot runs weekly for `pip` (uv), `npm`, `github-actions` and `docker`. Batch the minor updates and merge
them weekly.

## 9. Security baseline (demo bar)

Mapped to the OWASP Top 10 so it doubles as interview material.

| Risk | Control in this project |
|---|---|
| Broken access control | Path-scoped tenant dependency, role guards, record-level service filters, fitness tests, composite FKs, the 10-case test table |
| Cryptographic failures | argon2id passwords; random 256-bit tokens stored hashed; TLS everywhere once deployed (milestone D); S3 SSE |
| Injection | SQLAlchemy parameter binding only; no string-built SQL; Pydantic validation with max lengths |
| Insecure design | Explicit state machines, idempotency keys, outbox, ADRs |
| Security misconfiguration | Production settings validator; Caddy security headers (checked on the prod-like stack from P1-08); private bucket; no SSH and least-privilege IAM (milestone D) |
| Vulnerable components | Dependabot, pip-audit, npm audit, Trivy |
| Identification & auth failures | Rate limiting, generic login errors, session revocation, password reset revokes sessions; MFA at pilot |
| Integrity failures | Image tags = git SHA; lockfiles; OIDC deploy with no long-lived AWS keys (milestone D) |
| Logging & monitoring failures | Request IDs, JSON logs, audit events; Sentry and uptime alerts from milestone D |
| SSRF | No server-side fetching of user URLs. If one is ever added, use an allowlist |

## Quality bars

Three bars, in order ([ADR-0013](./adr/0013-local-first-deployment-milestone.md)). The first needs no AWS
account, domain or server.

### Demo-ready (end of week 8, local)

- [ ] Demo journeys 1–8 pass as Playwright tests in CI against the prod-like stack, and locally.
- [ ] The 10-case test table holds for every tenant endpoint, and the fitness tests are green.
- [ ] Every PR and merge builds the production image (tag = SHA), and the `prodlike` smoke passes:
      `/api/version` shows the SHA through Caddy.
- [ ] The backup and restore scripts work against the local stack. The scheduled restore test passed within
      the last 7 days.
- [ ] JSON logs carry request IDs, and `jobs-status` shows the queue. Both are checked on the prod-like
      stack.
- [ ] k6 laptop baseline recorded against the prod-like stack (p95 and error rate at 100 virtual users).
- [ ] Security headers (on the prod-like stack), dependency scans, secret scan and the ASVS L1 checklist
      reviewed. No open High findings.
- [ ] README with architecture diagram, ADR index, demo script and a walkthrough video recorded locally.
- [ ] Learning goal (not gating): James can whiteboard the request lifecycle, the tenant model, the session
      design, the outbox and the build pipeline (PR → CI → image → prod-like smoke) without notes.

### Deployed (milestone D)

Everything in demo-ready, plus:
- [ ] Every merge to `main` deploys to staging over HTTPS with no manual step. The deployed `/api/version`
      shows the SHA, and a rollback by SHA has been rehearsed.
- [ ] The staging smoke passes after every deploy. Every staging-only check in
      [D-06](./tickets/D-06-staging-verification-gate.md) has evidence (cookies over HTTPS, real S3 and SES,
      client IP behind the proxy, headers and TLS on the real domain).
- [ ] A nightly `pg_dump` to S3 runs, and a restore from S3 was tested within the last 7 days.
- [ ] Sentry, CloudWatch logs and uptime checks are live, with alerts reaching James.
- [ ] No inbound SSH, and no AWS keys stored in GitHub (OIDC only).
- [ ] Learning goal (not gating): James can whiteboard the deploy pipeline (merge → image in ECR → SSM →
      `deploy.sh` → smoke) without notes.

### Pilot-ready (before real residents)

Everything in demo-ready and deployed, plus [PILOT_READINESS.md](./PILOT_READINESS.md):
- staff MFA
- PITR with a measured restore drill
- a separate production environment
- maintenance-mode releases with a rehearsed rollback
- the privacy programme
- French UI if required
- UAT sign-off by building staff
- runbooks and an on-call owner
- a load test at pilot size
- data import
