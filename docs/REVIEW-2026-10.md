# 00 — Architecture And Plan Review

Reviewer stance: senior engineer / architecture reviewer / mentor.
Reviewed on 2026-10-13: `Recent_Plan/docs/*` (canonical set), `Plan/EC2-single-instance-deployment-plan.md`,
`Process/*`, `building-website/` (code, CI, compose, git history).
Updated 2026-10-13: the revised plan builds and tests locally first, and deployment is its own milestone
([ADR-0013](./adr/0013-local-first-deployment-milestone.md)). The findings below are unchanged; the fixes
that mention staging now point to milestone D.

## Verdict

**The technical direction is good. The plan is now the main obstacle to the project.**

You picked mostly sound architecture: a modular monolith on FastAPI + PostgreSQL, a tenant model of global
user → building membership → roles, a transactional outbox instead of Redis/Celery, private S3 with presigned
uploads, polling instead of WebSockets, explicit state transitions, and one EC2 host. Experienced engineers
would make most of the same choices.

The plan around those choices has grown into an enterprise launch programme: ~170 tickets, 17 milestones,
launch gates, UAT acceptors and recovery drills. It sits on top of a codebase with ~840 lines of backend code.
Planning has replaced building, and the plan's own gates block the work that is in progress right now.

The revision keeps the architecture, simplifies the parts the chosen topology makes unnecessary, and splits
the work into quality bars:

- **Demo-ready (week 8, local):** a tested, explainable product with three or four complete journeys,
  running on a production-like local stack and checked in CI.
- **Deployed (milestone D, right after):** the same product on AWS staging with continuous deployment,
  monitoring and nightly backups.
- **Pilot-ready (before real residents):** MFA, point-in-time recovery, a separate production
  environment, privacy compliance, UAT and runbooks.

## What to keep (strong decisions)

| Decision | Why it is right |
|---|---|
| Modular monolith (FastAPI, SQLAlchemy 2 async, Alembic, PostgreSQL 16) | Right size for 2 devs and one building. Microservices would add cost without benefit. |
| `User` → `BuildingMembership` → `MembershipRole`; no global `app_role` | Correct multi-tenant identity model. One person can live in building A and work in building B. |
| Server-resolved tenant context; never trust a client `building_id` without checking membership | The single most important security property of a multi-tenant app. |
| Composite tenant foreign keys `(building_id, id)` | The database itself prevents a cross-building reference. Cheap, strong, and good interview material. |
| Dated occupancy (unit history), not "current unit" columns | Unit turnover is a real privacy bug class: a new resident must not see the previous resident's packages. |
| Per-recipient notification rows | Gives simple read state and simple queries. |
| Transactional outbox + DB-backed worker; no Redis/Celery | At-least-once delivery with no new infrastructure. Business data never depends on the email provider. |
| Private S3 + presigned upload + server-owned `files` table | Correct pattern. Never trust client-supplied object keys. |
| Polling + React Query instead of WebSockets for MVP | Correct for the workload. WebSockets add stateful infrastructure for little gain. |
| Explicit action endpoints (`/pickup`, `/approve`) instead of `PATCH status` | Gives auditable, testable state machines. |
| uuid7 PKs, a naming convention for constraints, non-native enums (`app/models/*`) | Good choices already in the code. Keep them. |
| One EC2 + host Caddy + Docker Compose, same origin for SPA and `/api` | Cheap and simple. Same-origin also unlocks a much simpler auth design (finding H1). |

## Findings

Severity: **Critical** blocks progress now. **High** causes significant rework or risk. **Medium** costs quality
or learning. **Low** is polish.

### C1 — Planning has replaced building (Critical)

Evidence:

- About 21,000 lines of planning across `Recent_Plan/`, `Plan/`, `Process/`, `Past_folder/` and
  `building-website/docs/`, against about 840 lines of backend Python.
- Commits stop on 2026-06-04 and resume 2026-09-09 to 2026-09-11. Since then the deployment plan was
  rewritten (blue/green → single-instance on 2026-10-12) and the docs were revised. No code has changed.
- The in-progress branch `M2-T03_Core-Tenant-Schema_James` has `Building`, `BuildingFeature` and `Unit` as `...`
  stubs, with the old versions commented out below them.

Why it matters: momentum is the scarcest resource in a 2-person project. Every week spent refining the plan
for features 3–6 months away goes stale before it is used, and it makes the next coding session harder to
start.

Fix: rolling-wave planning. Detail only the next 2–3 weeks of tickets, keep later work as one-paragraph epics,
and ship a walking skeleton in week 2: the production image and SPA, smoke-tested in CI. Deployment to AWS
follows as milestone D ([ROADMAP.md](./ROADMAP.md),
[ADR-0013](./adr/0013-local-first-deployment-milestone.md)).

### C2 — Gates that cannot be passed (Critical)

Evidence:

- M0-T09 (permissions, occupancy, lifecycle) and M0-T10 (workload, targets, budget) need named
  building and product owners, budget owners and dated sign-off. `FEATURE_REGISTER.md` lists them all as
  **unassigned**.
- M2-T03 (in progress), M2-T12, M3-T02, M3-T07, M3-T12, M3-T14 and M5-T05 all depend on M0-T09 or M0-T10.
- The first-slice gate M7-T10 depends on staging infrastructure (M14-T03/T10/T13/T16/T17) and staff MFA
  (M4-T07 → M3-T14).

The pilot is 6–12 months away, so no one can make these decisions now. Read literally, the backlog says
nothing can start.

Fix: **decide by default, revisit with the pilot.**

- Record each policy default as an ADR with a "revisit when" trigger ([adr/](./adr/)).
- Move true launch controls into [PILOT_READINESS.md](./PILOT_READINESS.md).

### C3 — Launch controls front-loaded onto the first slice (Critical)

The first vertical slice requires all of the following:

- staff MFA
- refresh-token family revocation
- encrypted outbox token payloads
- S3 version pinning
- multi-tab context-switch leak tests
- staging with restricted email
- worker crash/lease recovery
- interrupted-deploy recovery

Each is valuable. Together, before anything works end to end, they guarantee the first slice never finishes.

Fix: the demo bar includes what makes the software *correct and secure by design*: tenant isolation,
authorization, idempotency, atomic transitions, an outbox, private files, and tests. The pilot bar adds what
makes it *operable for real people*: MFA, PITR, separate prod, monitoring on-call, privacy programme and UAT.
See [ENGINEERING_PRACTICES.md §Quality bars](./ENGINEERING_PRACTICES.md#quality-bars).

### H1 — Auth design is more complex than the topology requires (High)

Current design (M3-T02, PRODUCT_CONTRACTS §Sessions):

- short-lived in-memory access tokens
- identity-scoped rotating refresh families with replay detection
- cross-tab refresh coordination
- per-tab membership-bound access tokens
- a separate CSRF strategy

The project then adopted same-origin hosting (Caddy serves React and `/api` on one domain). Same-origin
removes the main reason to use bearer tokens in a browser app.

Fix ([ADR-0003](./adr/0003-same-origin-server-side-sessions.md)):

- **Opaque server-side sessions.** A random token in a `__Host-session` cookie (HttpOnly, Secure,
  SameSite=Lax), stored as a SHA-256 hash in a `sessions` table.
- **Revocation is deleting the row.** "Role change applies on next request" happens automatically,
  because authorization reads current DB state.
- **CSRF** is an Origin check plus a required custom header.
- **Building context** comes from the URL path (`/api/buildings/{id}/…`) and is validated against membership on
  every request ([ADR-0004](./adr/0004-path-scoped-tenancy.md)). Per-tab building selection then needs no
  per-tab tokens.

This deletes about 60% of the auth surface and is *more* secure, because there are fewer moving parts.
Explaining "why we did not use JWT" is also a strong interview answer.

### H2 — Documentation duplication and drift (High)

Evidence:

- The same rules (tenant context, outbox, files, sessions, phases, deployment) are restated in
  `AI_PROJECT_CONTEXT.md`, `backend_requirements.md`, `PRODUCT_CONTRACTS.md`, `BACKEND_INFRA.md`,
  `MILESTONES_AND_TICKETS.md` and `FEATURE_REGISTER.md`.
- There are at least three copies of the doc set:
  - `Recent_Plan/docs/`
  - `building-website/docs/`: stale, and missing `FEATURE_REGISTER.md` and `PRODUCT_CONTRACTS.md`
  - `Past_folder/docs(for Recent/`
- There are also several "entire plan/milestones" variants.
- An agent or teammate working inside the repo reads the stale rules.

Fix:

- One `docs/` folder **inside the repo**.
- Each fact lives in exactly one place: decisions in ADRs, work in tickets, how-to in the README.
- A short `CLAUDE.md` for agents.
- Archive everything else (ticket P0-01).

### H3 — Tickets are not shaped for AI agents or human review (High)

Evidence:

- Tickets mix concerns. M3-T02 covers sessions, cookies, CSRF, rotation, replay and multi-tab behaviour.
- Acceptance criteria live in other docs ("implement the contract in PRODUCT_CONTRACTS.md").
- Dependency fan-in is huge: M7-T06 depends on 9 tickets and M7-T10 on 8.
- The prose is compressed ("Hold restored outbound delivery until reconciliation"). Agents fill such
  ambiguity with guesses, and humans cannot review against it.

Fix: self-contained tickets of one PR each (≤ ~400 changed lines). Each has:

- explicit interfaces
- Given/When/Then acceptance criteria, including negative and tenant cases
- exact test commands
- likely files
- a risk tier

See [templates/TICKET.md](./templates/TICKET.md).

### H4 — Domain model gap: owners vs tenants vs occupants (High)

Evidence:

- `Process/initial database Structure/metropolis-data-schema.md` (the business-side schema) models a
  **Syndicate**, **Owners** who may own several units, **Leases**, **Contributions** charged to units, and an
  NEQ registration number.
- The plan models only "resident" plus occupancy.

In a condo, owner ≠ occupant: owners rent units out, and council members must be owners. Notices, votes,
financials and contributions target owners. Packages and maintenance target occupants. Adding this
later means rewriting every query that targets "residents of a unit".

Fix: model it now, cheaply. `unit_occupancies.relationship ∈ {owner, tenant, household}`
([ADR-0010](./adr/0010-unit-occupancy-relationship.md)). Owner-only features are later, but the data is right
from day one.

### H5 — Self-hosted Postgres operations scheduled too early (High)

The adopted EC2 plan is reasonable and is kept. But pgBackRest, continuous WAL archiving, RPO 15 min / RTO 4 h
drills, outbound-hold reconciliation and interrupted-deploy recovery are pilot-grade operations for a database
that holds only seed data until the pilot.

Fix ([ADR-0009](./adr/0009-backups-staged.md)):

- **Demo:** a scripted `pg_dump` plus a tested restore, built locally. It runs nightly to versioned S3 once
  staging exists (milestone D).
- **Pilot:** pgBackRest + WAL PITR, *or* a re-decision to RDS. Make that choice when the pilot is
  scheduled, with real cost and effort numbers.

### H6 — Likely Quebec context not reflected (High, pilot-blocking)

The business schema uses "Syndicate" and "NEQ", which are Quebec terms. If the pilot building is in Quebec:

- **Law 25** (Quebec private-sector privacy law) applies. It requires a person in charge of personal
  information, a confidentiality-incident register, privacy impact assessments, and care when data leaves
  Quebec.
- **French-language obligations** probably apply to a consumer-facing service.
- **CASL** affects commercial email and SMS.

None of this appears in the plan beyond a language-preference ticket.

Fix:

- Confirm the jurisdiction.
- Choose AWS `ca-central-1` (Montreal) now ([ADR-0008](./adr/0008-single-ec2-compose-caddy.md)).
- Keep the i18n strings infrastructure the Base44 app already has (`src/lib/i18n.js`).
- Add the privacy items to [PILOT_READINESS.md](./PILOT_READINESS.md).
- Get real legal advice before the pilot; this review is not legal advice.

### M1 — Repository hygiene (Medium)

- **Backend:** CI runs only `pytest`. M1-T05 promised lint and format checks, and there is no ruff or type
  checker.
- **Frontend:** lint is `continue-on-error` with 68 known errors, and the `typecheck` script covers only some
  files.
- **Dead code:** commented-out "Older version" models sit in `app/buildings/models.py` and
  `app/units/models.py`, with unused imports (`uuid4`, `Boolean`, …). Git history already keeps old versions.
- **Inconsistencies:**
  - `docker-compose.yml` runs Redis, and `settings.redis_url` exists, while every doc says "no Redis".
  - The `Dockerfile` sets `WEB_CONCURRENCY=2` while the deployment plan says 1.
- **Branching:**
  - Long-lived `develop` and `staging` branches suggest Git-flow, which is wrong for a 2-person team.
  - Branch names mix styles (`M1-T03-Frontend_Local_Run_Baseline`, `M1-T05_Baseline-CI-Checks_James`).
  - Commit messages like "deleting logs" and "merging with main" carry no information.
- `backend/.env.dev` is committed. That is acceptable only if it holds no secrets, so document that rule.

Fix: tickets P0-02, P0-03 and P0-04.

### M2 — No database testing strategy yet (Medium)

`tests/conftest.py` builds an ASGI client, and nothing touches PostgreSQL. Every important property in this
system lives in the database: tenant constraints, uniqueness, atomic transitions and outbox commits. Mocks
cannot prove any of them.

Fix (P0-05):

- Run tests against real Postgres: compose locally, a `services:` container in CI.
- Use one transaction per test with SAVEPOINT rollback.
- Run `alembic upgrade head` and `alembic check` (model/migration drift) in CI.

### M3 — The explanation workflow is passive and front-loaded (Medium)

`Process/` holds AI-written guides of 590–1,160 lines per ticket, written before the code exists (920 lines
for three tables).

- Reading is not learning.
- A guide written before implementation cannot explain the code that was actually written.
- The same AI that writes the code also reviews it, so its blind spots are correlated.

Fix: the build → review → explain loop in [AI_AGENT_PLAYBOOK.md](./AI_AGENT_PLAYBOOK.md).

- Humans frame acceptance criteria first.
- A *fresh* AI session reviews the work.
- Explanations come after the code, written by a fresh session, anchored to `path::symbol`, and stay short.
- Learning is active: quiz, explain-back and a hand-written change.

### M4 — Frontend migration lacks guardrails (Medium)

- 124 `.jsx` files and 1 `.ts` file.
- About 350 `base44.*` call sites across 33 entities and 30 pages.
- Heavy unused dependencies: Stripe, three.js, leaflet, jspdf, html2canvas, moment *and* date-fns.
- The plan says OpenAPI types "where practical".

Fix ([ADR-0011](./adr/0011-frontend-strangler-typescript.md)):

- OpenAPI types are mandatory.
- Migrated files become TypeScript.
- A CI **ratchet** ensures the count of Base44 references can only go down.
- Out-of-scope routes are hidden.
- Unused dependencies are removed as pages are migrated.
- An ESLint rule forbids `@base44/*` imports in migrated folders.

### M5 — Premature generality (Medium)

The following are deferred with a recorded reason:

- feature tiers and subscription metadata on buildings
- a separate RLS decision ticket
- a platform-admin role
- `ReportRead` tables
- optional vehicle, occupant, emergency-contact and document subresources
- SMS
- daily-operations adapters that "tolerate absent domain tables"

Deferring is a decision. Writing it down (ADR or backlog stub) prevents re-debating it.

### L1 — Polish (Low)

- `updated_at` uses `onupdate=func.now()`, which only fires for ORM updates. Document that bulk `UPDATE`
  statements must set it explicitly.
- `/api/ready` returns `str(exc)` in its 503 body. That can leak connection details; log the error and return
  a generic message.
- The settings default `aws_region="us-east-1"` disagrees with `.env.example` (`ca-central-1`).

## Risks that remain after the revision

1. **Review throughput.** With agents writing code, the bottleneck is human review. Keep PRs small, run CI
   before review, and treat risk tiers seriously.
2. **Base44 frontend quality.** Some exported pages may be faster to rewrite than to migrate. Decide per page
   when its slice starts; there is no blanket rule.
3. **The pilot moves.** If a pilot is suddenly confirmed for month 3, run the pilot-readiness checklist as its
   own 3–4 week phase. Do not cut tenancy tests or backups to make the date.
4. **Late deployment.** Staging is milestone D, after the local demo
   ([ADR-0013](./adr/0013-local-first-deployment-milestone.md)). Some behaviour only shows up on real
   infrastructure, so it surfaces late: HTTPS cookies, proxy client IPs, real S3 and SES, and memory on a
   small host. The prod-like stack in CI and D-06's checklist of staging-only checks keep this small. D's
   human prerequisites (AWS account, domain, SES) start a week ahead because of their waiting time
   ([ROADMAP.md](./ROADMAP.md)).
5. **Critical-path latency.** Lane A's tickets merge one after another. Total review and learning hours fit the
   budget; time spent *waiting* for review does not. Hence the review deadline and learning after merge
   ([AI_AGENT_PLAYBOOK.md](./AI_AGENT_PLAYBOOK.md#review-deadline)).
