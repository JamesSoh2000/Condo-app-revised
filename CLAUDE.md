Multi-building condo operations app: FastAPI + PostgreSQL backend replacing a Base44-exported React
frontend. One developer (James, solo since 2026-10-13). AI agents frame, build, review, explain and merge
tickets **autonomously** (ADR-0014, ADR-0017); no human checks a ticket before merge. James audits asynchronously
through `docs/HUMAN_INBOX.md` and the explanations in `docs/explanations/`.

## Where things are

- `backend/app/<feature>/` — models.py, schemas.py, service.py, router.py (package by feature)
- `backend/app/core/` — config, database, dependencies, errors (problem+json), pagination, schemas
  (`APIModel`, `InputModel`); security and csrf added in P2-01
- `backend/app/tenancy/` — TenantContext, get_tenant_context, require_roles, require_feature, building_router
- `backend/migrations/` — Alembic. `backend/tests/` — pytest against real Postgres
- `frontend/src/features/<domain>/` — migrated TypeScript code (added in P0-03). `frontend/src/api/` — typed
  client (`client.ts`, `errors.ts`, generated `schema.d.ts`; see its README) next to the legacy Base44 `*.js`
- `frontend/src/pages`, `src/components` — legacy Base44 JSX (shrinking; don't extend it)
- `docs/` — ARCHITECTURE.md, adr/, tickets/, explanations/, ENGINEERING_PRACTICES.md, AI_AGENT_PLAYBOOK.md

## Non-negotiable rules

1. **Tenancy.** Building data lives under `/api/buildings/{building_id}/…` on the building router, which
   depends on `get_tenant_context`. Every query filters by `ctx.building_id`. Another building's records
   return 404, never 403. (ADR-0004)
2. **Related IDs.** Every ID from a request body (unit_id, file_id, membership_id…) is loaded with
   `building_id = ctx.building_id`, and new references use composite FKs `(building_id, x_id)`. (ADR-0005)
3. **Record visibility.** Residents see only their own records. A unit-addressed record is visible only if it
   was created during the viewer's occupancy period. Use the domain's `visible_*` query helper. Never
   hand-roll this filter.
4. **Auth.** Server-side session cookie. Never add JWTs, localStorage tokens or a new auth dependency.
   Unsafe methods need the CSRF middleware. Do not exempt routes without an ADR. (ADR-0003)
5. **Transactions.** Only write use-cases in `service.py` call `await db.commit()`, exactly once. Helpers
   (`record_audit`, `notify`, `enqueue`, `attach_file`) never commit.
6. **Side effects.** Email and other external calls happen only in the worker through `enqueue()`. Never call
   SMTP/SES from a request. (ADR-0006)
7. **State changes.** Use action endpoints (`POST …/{id}/pickup`) with a conditional
   `UPDATE … WHERE status IN (…) RETURNING`. No `PATCH status`. Zero rows → 404 or 409 `invalid_transition`.
8. **Errors.** Services raise domain errors from `app/core/errors.py` and get problem+json
   with a stable `code`. Never return `str(exc)` to clients.
9. **Files.** Never accept S3 keys from clients. Use `file_id` from the files module. Downloads authorize
   through the owning record. (ADR-0007)
10. **Secrets & PII.** Never log tokens, passwords, cookies, file contents or full request bodies. Audit
    metadata holds IDs and field names only.
11. **Migrations.** Read and fix autogenerated migrations (partial indexes, NULLS NOT DISTINCT, server
    defaults, enums). Expand/contract only. Never edit a migration that has been merged.
12. **Frontend.** No `@base44/*` imports under `src/features/`. Data goes through `src/api/client.ts` and
    React Query hooks with keys `['b', buildingId, …]`. New and migrated files are TypeScript.
    Regenerate API types when the API changes.
13. **No new infrastructure** (Redis, WebSockets, Celery, new AWS services) without an ADR.

## Conventions

- Python 3.14, full type hints, ruff + mypy clean. Pydantic `XCreate`/`XOut` schemas with `max_length` on
  strings. Never return ORM objects.
- Reuse: `app/models/base.py` (Base, naming convention), `app/models/mixins.py` (uuid7 PK, timestamps),
  `app/models/types.py` (`database_enum`), `app/core/dependencies.py` (`get_db_session`),
  `app/core/time.py` (`validate_timezone`). Register every new `models.py` in `app/models/registry.py`.
- Names: tables plural snake_case; enum values lowercase; audit actions `<domain>.<past_verb>`; job kinds
  `<domain>.<verb>`; operation IDs `<domain>_<verb>`.
- Tests: behaviour names (`test_resident_cannot_see_other_residents_package`). Use the world fixtures in
  `tests/conftest.py` (see `tests/README.md`) and the tenant helpers in `tests/helpers/tenancy.py`. Apply
  the 10-case table in docs/ENGINEERING_PRACTICES.md §7 to every tenant endpoint.

## How to work a ticket (docs/AI_AGENT_PLAYBOOK.md; `/build-ticket <ID>` runs it all)

1. Read the ticket in `docs/tickets/`, the ADRs it links, and the **current code** before planning.
   The docs describe targets; the code is the truth. Check `docs/HUMAN_INBOX.md`: stop if `paused`.
2. Frame, then plan, without waiting for approval: sharpen the criteria (never loosen one silently), write the plan
   into the PR. Decide open questions with the playbook's **decision rules** and record each one in the PR when you
   make it (alternatives, tradeoffs, basis); lasting decisions get an ADR and an inbox "Decisions to audit" line.
3. On a **stop rule** (human-only resource, contradicts an ADR/scope/rule above, needs a weaker gate, review not
   converging, unnamed outward-facing action): set the ticket `blocked`, write it in the inbox, move on. Never guess
   past one.
4. Tests first per criterion. PR ≤ ~400 non-test lines: cost the error and race criteria, size UI from a measured
   component of its kind (P4-01, P4-08a–c); tests don't count, never cut them. Stay in scope; extras: follow-ups.
5. Branch `<ticket-id lowercase>-<slug>` in its own worktree. Rebase onto `main` before review and merge.
6. **Never review your own work.** The review runs in fresh sessions (subagents). Fix confirmed findings test-first;
   at most 3 review rounds. You write the explanation yourself, last (after the final `MERGE`, the rebase and green
   CI), following a reality pass: re-read the diff, the cited files and the tests from disk, run them, and keep
   implemented behaviour, design rationale and limitations apart. What you remember of building it is not a source
   (ADR-0017).
7. Merge (`gh pr merge --squash`) only when the playbook's **merge gate** passes. End with the handoff block.
8. In explanations and answers, reference code as `path::symbol`, not bare line numbers. Name the PR and revision you
   describe, and mark a "why" no record states as inferred.

## Context hygiene

Everything a command prints is re-read on every later turn, so don't print the same text twice.
- Large diff: `git diff --stat` first, then one path's patch at a time. A reviewer still reads every changed path;
  the stat orders the reading and never replaces it.
- `gh pr view --json <only the fields you need>` (`-q` to cut further), once per step. Fetch again only after the PR
  changed (a push, a review round, a comment).

## Never

- Touch staging/production data or credentials, `.env` files with real values, branch protection or CI permissions,
  unless the ticket says so.
- Loosen a protected gate (CI jobs, lint/type config, fitness or existing tests, check scripts, these rules) to make
  CI pass. Fix the cause, or block the ticket.
- Add dependencies without saying why in the PR.

## Lessons learned (from docs/AGENT_MISTAKES_LOG.md)

- When fixing a review finding, also test the fix on its neighbours: error paths, malformed input, the same check one
  notch weaker (warn vs error), every other option the changed code path takes, and every other way to reach the same
  state (another command, another response path). A fix that only covers the reported case gets reopened (P0-05 round
  3, P0-03a round 2, 2026-10-14; P1-07 round 2, P1-08 round 1, 2026-10-16). For state and concurrency fixes, list
  these ways before the first review: a second instance of the action, Back/Forward (one route's URL change keeps the
  page mounted: key it by `useLocation().key`), an abandoned caller, a failure, a server-driven change (a refetch,
  `/me`) (P2-06a–c, P4-07a; 2026-10-20), and every other fetch that can interleave with a list's refresh: the next
  page, a focus refetch, a failed refresh, an awaited `onSettled` (P4-08b R1–R3; 2026-10-21).
- Don't claim an effect ("unbreaks main", "new revisions come out ruff-clean") until you have run the thing that
  shows it and pasted the output (fix PR #3, P0-02, 2026-10-14).
- Prove a gate, check or health signal can fail before trusting it: make it fail once on purpose (a probe PR, a
  mutation, a failing init script) and paste that output too. Four checks passed vacuously in P0 (P0-03a fence,
  P0-03b route check, P0-04a LocalStack health, P0-05 ORM test; 2026-10-15). Commit before mutation probes:
  `scripts/mutation-probe.sh` refuses a dirty tree, restores and re-runs the baseline (P1-03, P1-05; 2026-10-16).
- Write in the PR only what is already on the branch. Until the bookkeeping commit exists, say "will be added to the
  inbox / <ticket> in step 6", not "listed in" (P1-04, P1-05, P1-07; 2026-10-16).
- Don't write from a value read before a slow `await` (argon2, a lock wait): re-check it after the lock, with a fresh
  clock, in the writing statement. Expiry must be final (P4-02b ×4; 2026-10-20).
- Validate caller input by what Postgres accepts, not Python: lone surrogates, NUL, NaN and byte lengths fail at
  flush as `DBAPIError`, not the documented `ValueError` (P3-02 ×2, P3-03; 2026-10-18).
- Check focus and accessible names in Chromium, not only jsdom (no CSS or click focus; P2-06c, P4-07a, P4-08b/d).
- A query whose component can unmount and come back while its data changes elsewhere needs `refetchOnMount: 'always'`
  or `gcTime: 0`, or the 30 s `staleTime` serves the old answer (PR #98 R3 M1, P4-08d R1 F2; 2026-10-21).
- Check code with a parser (TypeScript's, Python's `ast`), not a regex: generics, multi-line calls, comments, nested
  objects and aliased imports escape text matching (P4-09 F4, PR #108 R1-F1 and R3-F1; 2026-10-22).
